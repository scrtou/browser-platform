# DEV-040 · 迁移准备缺少控制器能力核对

状态：已解决（能力门槛、失败清理、生产保护与最终组合部署）。发现日期：2026-09-15，生产复核日期：2026-09-17。关联 [R4B](../work-items/R4B-2026-09-14-target-client-migration.md)。

## 预期与实际

R4B 要求 r7 应用、冻结产物、正常退出、显示材料及控制器能力匹配后才启动新代次。问题发现时，`prepare-migration.py` 只核对旧策略、journal、资源及镜像中的环境重放，没有查询实际控制器的能力清单，也没有把镜像的显示认证/正常退出要求与控制器比较。

2026-09-15 继续工作时，生产 Adapter 配置已引用 `personal-camoufox-r7` / `camoufox-personal-r7-guard`，绑定状态为 `unknown`；Guard/Relay 仍运行，正式 Worker 不在容器清单。独立调试容器报告 `SESSION_AUTH_INPUT_INVALID`。控制器仍是旧 lifecycle 部署，尚未发布 R5D 的显示材料支持。原工作项和进度只写到“准备候选/Personal 停止”，遗漏此前已经发生的配置切换和失败启动。

详细既有材料保存在被忽略的 `infra/sealskin/runtime/r4b-production-migration-2026-09-15/candidate-1/`；新的核对、处理和回归材料使用独立目录，不覆盖失败历史。Work 与旧 Personal Home、备份、journal 均保留。

## 处理决定

修复实现：迁移准备必须核对实际控制器和目标镜像所需能力，不兼容时在生成可安装候选前拒绝。通过现有生命周期对失败代次执行归属核对、停止/清理；资源未证明释放前保留 `unknown` 和操作日志。r7 的实际发布仍须满足显示 tmpfs、匹配控制器/Adapter、入口授权及客户端等发布条件，不能降低要求或换用旧产物冒充 r7 完成。

同步 R4B、进度、路线图、迁移操作和组件说明；验收保留旧失败、资源处理结果及能力拒绝回归。完整迁移和 R5 发布仍未完成。

## 修复复核

失败代次已通过原生命周期 stop 清空；独立调试容器正常停止并清理，Home、备份和 journal 保留。准备器已增加精确镜像/实际控制器能力检查，Adapter 已增加创建 Home 前、启动/复用及恢复前和启动后的检查；生产 Personal 的启动保护已上线，旧控制器仍保持。

最终代码复核发现，能力漂移也可能在 launch 返回后被检测到，此时占用正确保留为 `unknown`，但通用 503 文案仍写“未启动新会话”，超出了该路径能够证明的事实。候选 4 改为维护提示，保留原状态与拒绝行为，并重新验证受影响的 HTTP 检查。用户原 r7 测试期间 QA 保持候选 3；本次窗口修订的 QA 维护中已同步候选 4，生产/QA 运行二进制摘要一致，没有为纯文案更新打断用户测试。

534 项控制、10 项准备检查及适用 Go test/race/vet 通过；该阶段的生产 Personal POST start 返回 503、保持 stopped/资源 0，Work GET 200 / POST start 303 复用原会话。50 个 Go 源文件、四个二进制、32 个实际控制文件和构建输入已核对；文档链接、语法、格式与公开敏感扫描通过。2026-09-17 最终共享组合部署后，Work 与 Personal 均由能力版本 1/1 的匹配代次运行，服务器端上线检查通过。具体版本和证据见 [R4B 阶段验收](../../infra/sealskin/target-client-migration-acceptance-2026-09-15.md)。目标 Mac 生产复测与正式重启属于 R4B/R2 的剩余验收，不再是本偏差的实现缺口。
