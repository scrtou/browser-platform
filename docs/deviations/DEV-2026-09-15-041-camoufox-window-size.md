# DEV-041 · 目标客户端浏览器窗口偏小

状态：已解决。目标 Mac 已确认 `fill-r10` 画面铺满且点击映射正常；窄视区的非等比缩放取舍已记录。发现日期：2026-09-15。关联 [R4B](../work-items/R4B-2026-09-14-target-client-migration.md)。

## 预期与实际

用户在目标 Mac / Trilium 实机测试后要求浏览器与此前 Personal/Work 一样大。r7 观测报告显示远端 screen 为 1920×1080，而浏览器 outer 为 1600×900、inner 为 1600×844，窗口位于 (160, 90)；用户反馈浏览器界面太小。五个目标点击和基础输入通过不能证明显示大小符合使用要求。

Mac 本机为 1280×800、正常显示；上述 screen、DPR 和窗口数字是远端浏览器观测，不能当作 Mac 的显示缩放。原 Firefox 与 r7 的桌面/窗口启动方式、冻结产物约束和客户端缩放仍须从实际代码核对。

## 处理决定与边界

先核对默认窗口、桌面适配与原 Firefox 的实际差异，再修复或修订与用户新要求冲突的窗口契约。若需要改变冻结的环境字段，应生成新的匹配产物并按范围重验；不把临时放大、虚报 screen 或忽略产物漂移当作正式修复。实机 QA 保持独立，生产 Work 和旧 Personal Home 不参与故障操作。

代码核对确认 r4 起为避免 Openbox 最大化后 inner/outer 不一致，加入了不最大化、无外边框规则；r7 沿用冻结的 1600×900 和中心位置 (160, 90)。本轮按用户要求修订默认窗口为远端桌面的 1920×1080、位置 (0, 0)，保留 screen/DPR、r7 镜像、原始完整 BrowserForge 结果、设备参数、seeds 与 preferences，只生成新的窗口修订产物并完成完整重放及正常桌面验收。客户端仍按视窗缩放固定远端显示，不静默改变 screen/DPR。

验收页此前只有文字输入区，无法显示粘贴图片；桥接成功提示不能替代目标页面处理结果。本轮补上原生 paste 图片预览区和实际尺寸/摘要记录，供 Mac 验证端到端截图粘贴；不修改已验证的生产剪贴板桥接。

窗口大小、截图预览及受影响客户端分项复测前，R4B 保持进行中。文件按钮/拖放已获用户确认，输入法为 macOS 系统输入法；截图目前只确认传输成功提示，尚无预览结果。

首轮新产物验证通过结构检查与 11 类启动拒绝；重放在启动第一个浏览器前因引用已清理的 R5D 临时网络失败。失败报告保留，改用本轮独立网络和受限 `example.com:443` QA 代理后重跑完整验收；没有放宽网络检查或复用生产 Relay。

第二轮已进入真实浏览器，但新增窗口断言误复用了存储期望值变量，导致标签页存储比较拿整数作预期；三类实际存储值一致。修正测试变量后重跑完整验收，保留第二轮失败和隔离资源清理记录，不将其记为产物通过。

r8 第三轮完整产物验收通过，23 次窗口/存储观测一致；换入正常 QA 桌面后，Openbox 的 `keepBorder=yes` 仍为 undecorated 窗口保留四侧各 1 像素。窗口外框已铺满 1920×1080，但原生客户区被压为 1918×1078，与重放时的 1920×1080 客户区不同。继续修复桌面配置为 `keepBorder=no`，以 r7 的精确镜像增加小型桌面层，保留窗口和设备配置后生成 r9 产物并重验。r8 仅通过重放，不能作为最终桌面完成证明。

桌面层首次构建把本地 image ID 直接用于 BuildKit `FROM`，被当作仓库名查询而失败，未生成镜像。后续使用核对到同一精确 image ID 的本地标签作为构建引用，`worker-base` 标签仍保存完整 image ID；失败日志与旧构建输入保留。

## 最终修订与复核

r9 绑定新桌面镜像 `sha256:10f6420a1e409ce98cdc18a8830f023b46a30e4697d258126d6bf591c8fcc371`，完整 `all` 产物验收通过：结构检查、11 类启动拒绝、两个 Home 各 10 次重建和离线恢复，23 次观测一致。正常 `/init`/Openbox 桌面客户区实测 (0, 0)、1920×1080、四侧边框 0，网页 outer 1920×1080 / inner 1920×1024，与重放一致。

原 QA 入口已升级 r9，同一独立 Home 保留，三类存储与用户 17:48 UTC 报告一致。Linux 公网授权/真实串流、1280×800 的 5 次及三组视窗/DPR 的 15 次可信点击、Unicode/composition、导航/标签/滚动、Files/拖放远端摘要、断线/离线重载通过；新截图区经原生 paste 实际显示 320×160 PNG，可信事件、尺寸与像素摘要匹配。客户端图像已人工核对，完整运行资源身份保持。

目标 Mac 随后确认 r9 的五个按钮可点击、页面可见实际图片预览，但画面仍未铺满 Trilium 视区，并指出 Work 显示正常。只读核对发现远端 X11 桌面与 Camoufox 窗口均已是 1920×1080、位置 (0, 0)、边框 0；问题来自 Selkies 对固定 16:9 显示使用 `contain`。已有 1280×800 客户端截图也复现为 1280×720 画面，上下各约 40 像素留边。先前“窗口铺满远端桌面”的证据只证明远端原生几何，不能证明固定画面铺满不同比例的客户端视区。

本轮保留远端 1920×1080、页面 screen/DPR、r9 产物和完整桌面，修订固定显示的客户端映射：WebRTC 与 WebSocket 两条手动分辨率路径都将完整画面按客户端宽、高分别映射到整个视区，输入层使用相同边界进行横纵坐标换算。这样不会裁掉远端桌面，也不会像 Work 一样动态改变远端分辨率；客户端与 16:9 不同宽高比时会发生非等比缩放，所以 Trilium 未横向展开时文字可能显得细长，这是显示层拉伸，不是 Camoufox 网页字体或远端 CSS 改变。安装器仍只接受固定上游摘要、生成新资源并原子切换，未知上游或被修改资源继续拒绝。

新客户端包为 `native-clipboard-88dfb32aa9f275e1`，完整摘要 `88dfb32aa9f275e1b2e3c6ba76f21c02c40cb0e608b4375370282b097e3e597c`，运行资源为 `index-native-paste-628d1314a06310e5.js`。同一 r9 环境和 QA Home 经原生命周期 stop 后以 `camoufox-r4b-client-fill-r10` 新代次启动；临时账号和固定入口不变。1280×800 检查确认 canvas/输入层均为 (0, 0)、1280×800，无原上下留边，五次点击、实际图片像素、刷新重连和三类存储通过；1920×1080/1、1280×720/1、1000×760/2 三组边界均完全贴合并有 15 次可信点击，远端仍为 1920×1080 / DPR 1。一次坐标回归在读取点击报告时遇到瞬时空队列，失败材料保留，未改代码原样重跑通过。

产物重放使用的临时代理和网络已清理；Mac QA 及其独立入口/账号/显示材料仍保留。生产 Work、生产配置和进程身份在切换及复测前后保持。用户已确认 `fill-r10` 在 Trilium 中铺满且点击映射正常，同时观察到窄视区下字体变细长、分辨率观感与 Work 不同；这符合固定 1920×1080 画面铺到非 16:9 视区的预期。用户的 r9 按钮与实际图片预览已记录通过；该显示偏差已解决为明确的固定分辨率取舍，R4B 仍受生产迁移条件约束。证据位置见 [阶段验收](../../infra/sealskin/target-client-migration-acceptance-2026-09-15.md)。
