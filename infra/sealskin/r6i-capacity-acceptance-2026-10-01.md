## 资源实测

主机约 5,924 MiB RAM / 4 CPU；保留已有生产负载。94 份 cgroup v2/主机样本覆盖约 100.1 秒，含单浏览器、双浏览器、启动及稳定阶段；稳定阶段在 Worker 内每两秒执行有界认证 HTTPS。真实 Firefox 进程已观测；没有 GUI 视频、复杂网页或多标签交互负载。

| 资源 | 浏览器 A | 浏览器 B |
| --- | --- | --- |
| 内存峰值（cgroup memory.peak） | 523.7 MiB | 561.4 MiB |
| PID 峰值 | 259 | 259 |
| 提交启动至浏览器进程出现的完整耗时 | 5.55 秒 | 5.66 秒 |
| 内存 / CPU / PID / shm 配置且实际核对 | 1 GiB / 1 CPU / 512 / 256 MiB | 同左 |
| OOM / OOM kill / memory max 事件 | 0 / 0 / 0 | 0 / 0 / 0 |
| CPU 限流期间数 | 47 | 56 |
| 采样期间 swap 峰值 | 0 | 4 KiB |

CPU 配额已生效且启动期间出现限流，不能宣称无性能影响。Docker 默认 MemorySwap=2 GiB（RAM+swap），不等于禁止 swap。控制器内存峰值 151.0 MiB / 31 PID；两个 Relay 峰值 17.4 / 15.1 MiB、各 7 PID；Guard 约 11.3 MiB。主机最低 MemAvailable 为 1,617.8 MiB，磁盘最低可用 9,688 MiB。

本次验证上限为 **两个隔离浏览器的上述限定负载**，没有测试第三个，也不是主机物理极限。为了在现有生产负载下给每个新增 Worker 留足完整 1 GiB 内存预算，按准备阶段可用约 2,420 MiB，预留主机 1,024 MiB、QA 控制器 256 MiB、每组 Worker+Relay/Guard 1,088 MiB，保守新增预算为 `floor((2420-1024-256)/1088)=1`。双浏览器低负载实测通过不扩大这一最坏预算。

运行建议：在当前其他服务保持的条件下，同时新增一个有 1 GiB 上限的浏览器；并发启动上限取 1，磁盘最低保留建议 4 GiB。全局 max_active_profiles 需按同一 Adapter 管理的存量和独立服务重新核对，不能把“新增 1”直接写成生产总上限。当前生产既有实例并非全部有硬限制，任意网页负载仍可能改变余量；增加常驻数、视频或标签数前须在对应负载复测。以上均为候选建议，未写入生产。
